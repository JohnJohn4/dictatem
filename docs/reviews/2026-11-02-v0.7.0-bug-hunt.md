# Dictatem v0.7.0: fresh-eyes bug hunt

**Nothing launch-blocking found.** No defect found here kills the hotkey or the
daemon, and none loses a dictation: the Most-recent dictation buffer, the epoch
drop of stale results and the top-level `try/except`s all held up under
review. There is one **High** finding: the *user's own* clipboard can be lost
when two dictations land within 1.5 s of each other. It already existed in
v0.6.4, and v0.7.0's full-format snapshot carries the same flaw. It is worth
fixing in a patch release.

- **Scope:** `git diff v0.6.4 v0.7.0 -- src/`.
- **Method:** read the code against `CONTEXT.md`, the README and ADRs 0001,
  0004, 0013, 0016, 0023, 0025, 0026 and 0028, then prove suspicions with
  tests.
- **Proving tests:** `tests/test_bughunt_core.py`,
  `tests/test_bughunt_paste.py` and `tests/test_bughunt_transcribe.py`. Each
  one is `xfail(strict=True)` with the finding ID in its reason, so fixing a
  finding turns its test into an XPASS failure and forces the marker's
  removal.
- **Not tested:** nothing ran on a real Mac. The macOS-only items are marked
  Plausible.

Severity key:

- **High:** a user hits it in normal use, or it causes data loss or a dead
  hotkey.
- **Medium:** a real defect, but it needs a less common path or it recovers on
  its own.
- **Low:** an edge case, or the wrong message.

## High

### H-1: Back-to-back dictations lose the user's clipboard, and the second paste can land the wrong text

- **Where:** `src/dictatem/paste/pipeline.py:216` and `:240-249`.
- **Scenario:**
  1. Dictation A saves the user's clipboard U, puts A's text on the clipboard,
     sends Ctrl+V and schedules "restore U" 1.5 s later.
  2. Dictation B pastes inside that window. A short push-to-talk on a warm
     GPU, or saying "paste" straight after, gets there. B's `save()` snapshots
     A's temporary text instead of U.
  3. The two restores then fire in order: U, then A.
- **Effect:** the clipboard ends up holding **dictation A**, and U is gone for
  good. If restore-U fires between B's Ctrl+V and the moment the target app
  reads the clipboard, the app pastes U where B's dictation should go. U might
  be a password copied from a manager.
- **Confidence:** Confirmed by test
  (`test_back_to_back_dictations_restore_user_clipboard`). The clipboard ends
  as `'dictation a '`. This also happened in v0.6.4.
- **Fix:** keep one pending-restore snapshot, owned by the daemon or pipeline.
  If a restore is still pending when the next paste starts, reuse that
  snapshot instead of calling `save()` again, and cancel or supersede the old
  timer, so only the last restore puts U back. Combine with M-3.

## Medium

### M-1: A 200–250 ms press loses its release; the mic stays open in PRESSED with no silence or max-duration stop

- **Where:**
  - `src/dictatem/hotkey/classifier.py:240-251`
  - `src/dictatem/daemon.py:331-347` (`_HotkeyBridge.tick`)
  - `src/dictatem/daemon.py:634` (`check_silence`)
- **Scenario:**
  - `HOLD_START` is emitted only by the GUI tick (every 50 ms). At key-up the
    classifier returns `TAP` only if `elapsed < tap_threshold_ms`. Otherwise
    it returns `HOLD_END` only if the tick has already emitted `HOLD_START`.
  - A release at, say, 230 ms that comes after the threshold but before the
    next tick therefore produces **no event**.
  - The state machine has already handled `KEY_DOWN`, so `RECORD_START` ran
    and the mic is open. It stays in `PRESSED` indefinitely.
  - `check_silence` only acts in `PTT_REC`/`TOGGLE_REC`, so neither the
    silence timeout nor `max_recording_seconds` ever stops it.
- **What the user sees:** the pill stays up, recording, until they press
  again. The tray **Stop** item sends `KEY_UP` with `now_ms=1000` against a
  real monotonic `key_down_at`, so its first click moves to `TOGGLE_REC`
  instead of stopping. It takes two clicks.
- **How likely:** the window is up to 50 ms wide, right at the tap/hold
  boundary. It gets wider whenever the GUI thread is busy, for example during
  the modifier-release wait or paced typing.
- **Confidence:** Confirmed by test
  (`test_release_after_threshold_but_before_tick_still_stops`). This also
  happened in v0.6.4.
- **Fix:** in `_on_key_up`, when the combo breaks with
  `elapsed >= tap_threshold_ms` and `HOLD_START` was never emitted, return
  `HOLD_END`. The bridge maps it to `KEY_UP`, and `PRESSED + KEY_UP` with that
  elapsed time already goes to transcribe. Also make the tray Stop use the
  real clock.

### M-2: Rewriting the config doesn't escape TOML strings, so a backslash or quote corrupts config.toml

- **Where:** `src/dictatem/config.py:616` (`_toml_value`); triggered by
  `daemon.py:2545-2549` (`_persist_autostart`).
- **Scenario:**
  1. A user points `[model].name` at a local model directory
     (`name = 'C:\models\whisper-large-v3'`; faster-whisper accepts a path),
     or has a `"` in any string value.
  2. They toggle **Start at login**.
  3. `write_config` emits `name = "C:\models\whisper-large-v3"`, where `\m` is
     an invalid TOML escape.
  4. On the next launch the file won't parse. That session runs on the
     hardware defaults, read-only, with "Dictatem couldn't read config.toml".
- **Effect:** the user didn't edit the file, but Dictatem broke it. This is
  separate from **#288** (the toggle dropping comments and unknown keys), but
  the same fix would close both.
- **Confidence:** Confirmed by test
  (`test_rewritten_config_round_trips_string_values`, two cases).
- **Fix:** escape `\` and `"` (and control characters) in `_toml_value`, or
  emit `json.dumps(value)`, whose escapes are valid TOML basic-string escapes.
  Better still, fix #288 by editing only the `autostart` line in place.

### M-3: The deferred clipboard restore overwrites anything the user copies within 1.5 s of a paste

- **Where:** `src/dictatem/paste/pipeline.py:225-249`.
- **Scenario:** the user dictates, then within 1.5 s presses Ctrl+C or uses
  the tray's **Copy last dictation**. The restore runs unconditionally and
  replaces what they just copied with the old clipboard.
- **Confidence:** Confirmed by test
  (`test_deferred_restore_does_not_clobber_a_copy_made_meanwhile`).
- **Fix:**
  - After `set_text`, record the clipboard change counter:
    `GetClipboardSequenceNumber` on Windows, `NSPasteboard.changeCount` on
    macOS.
  - In `_restore`, skip the restore if the counter has moved.
  - This needs a small new `ClipboardIO` method. Take the reading after the
    adapter's own marker writes.

### M-4: `save()` gets no contention retry, so one race with the Win+V monitor holds the dictation

- **Where:** `src/dictatem/paste/win32_clipboard.py:157-162`;
  `src/dictatem/paste/pipeline.py:216`.
- **Scenario:**
  - `save()` calls `OpenClipboard` itself.
  - Only `open()` goes through `_open_with_retry`, the #145 fix for exactly
    this race.
  - If the clipboard history monitor, or another app reacting to a recent
    clipboard change, holds the clipboard for a moment during `save()`, an
    `OSError` aborts the paste. The dictation is held, and the user must say
    "paste".
- **Possible link:** this could be behind **#269** ("first dictations after a
  fresh install didn't paste, intermittent"). That issue's log should show
  `Paste failed (… dictation) — held for recovery` with a contention
  traceback from `save`.
- **Confidence:** Confirmed by test
  (`test_transient_contention_on_save_is_retried_like_open`). The link to
  #269 is Plausible.
- **Fix:** run `save()` through the same bounded retry as `open()`.

### M-5: An interrupted Apple-GPU (MLX) model download is never repaired; every launch falls back to CPU

- **Where:** `src/dictatem/transcribe/mlx_backend.py:44-62` (`_local_snapshot`).
- **Scenario:**
  - The first-run MLX fetch is interrupted: network drop, Quit, or the lid
    closing.
  - huggingface_hub writes `refs/main` and the snapshot folder before the
    files. `snapshot_download(local_files_only=True)` then returns that partial
    folder without checking that the files are complete (the library says so
    in a comment).
  - `LocalEntryNotFoundError` is never raised, so the online download never
    runs again.
- **Effect:**
  - Every later load fails because the weights are missing.
  - Every launch shows "MLX failed to load", and the session runs on CPU.
  - Nothing repairs it short of the user deleting the HF cache by hand.
  - faster-whisper isn't affected, because it tries online first.
- **Confidence:** Confirmed by test
  (`test_mlx_partial_snapshot_is_refetched_not_returned`). The real-Mac
  behaviour is unverified.
- **Fix:** check the returned snapshot has its weights (`config.json` plus
  `weights.npz` or `*.safetensors`), and call `snapshot_download(repo)` online
  if it doesn't. Or try online first and fall back to `local_files_only` on a
  connection or offline error.

## Low

### L-1: Preload finishing mid-recording hides the live recording pill

- **Where:** `src/dictatem/daemon.py:1610-1616` (`check_loading_overlay`).
- **Scenario:** with `[startup].preload_model = true`, or after tray
  **Preload Model**, the user starts dictating while the load is still running.
  When the load (and the LLM warm-up) finishes, `_preload_pill_active` is
  still set, so `overlay.hide()` runs and the recording pill vanishes while
  the mic is still recording. The dictation itself still works.
- **Confidence:** Confirmed by test
  (`test_preload_completion_does_not_hide_recording_pill`).
- **Fix:** clear `_preload_pill_active` in `_do_record_start`. Or only
  `hide()` when the state machine is `IDLE`.

### L-2: Check for Updates goes dead after a started upgrade that fails before stopping the daemon

- **Where:** `src/dictatem/upgrade/qt_update_check.py:142-145`.
- **Scenario:** after the user confirms, `_busy` stays `True` on purpose: the
  installer is expected to stop and replace this daemon. If the installer
  fails first (the `irm` download fails, or the user closes the PowerShell
  window), the daemon keeps running. From then on every **Check for Updates…**
  click returns silently until Restart.
- **Confidence:** Plausible.
- **Fix:** clear `_busy` after a generous timeout (for example 10 minutes),
  or on the next click once that time has passed.

### L-3: A `set_text` failure leaves the clipboard open and emptied

- **Where:** `src/dictatem/paste/pipeline.py:217-219`.
- **Scenario:**
  - `EmptyClipboard` succeeds, then `SetClipboardData` raises.
  - `close()` is never called, so the daemon's thread keeps the system
    clipboard open and other apps' copy/paste fails until the next
    open/close.
  - The emptied clipboard is not restored.
  - The dictation itself is held correctly.
- **Confidence:** Confirmed by test
  (`test_set_text_failure_still_closes_clipboard_and_restores_user_data`).
  Rare.
- **Fix:** wrap `set_text` in `try/finally: clipboard.close()`, and attempt
  `clipboard.restore(saved)` on failure.

### L-4: Trigger Fire types the replacement even if the Backspace phase stopped short

- **Where:**
  - `src/dictatem/paste/win32_keystroke.py:421-427` and `:470-480`
  - `src/dictatem/paste/pipeline.py:209-210`
- **Scenario:**
  - A Backspace chunk is dispatched short, for example because a UAC prompt,
    the lock screen or a desktop switch arrives mid-phase.
  - `_dispatch` stops that phase, but `send_backspaces` returns nothing.
  - `send_text` then types the full Transform output on top of a half-deleted
    Last Paste.
  - The daemon records that as the new Last Paste.
- **Confidence:** Confirmed by test
  (`test_trigger_fire_does_not_type_after_backspace_phase_fell_short`). In
  the test, 40 Backspaces were requested and 8 sent, then the text was still
  typed.
- **Fix:** have `send_backspaces` raise on a short dispatch, so the pipeline
  skips `send_text` and the daemon shows the error flash without setting Last
  Paste.

### L-5: After a failed load, the next successful preload can be idle-unloaded at once

- **Where:** `src/dictatem/transcribe/lifecycle.py:200-202` and `:257`.
- **Scenario:**
  1. A dictation's load fails, for example offline. `_finish_transcription`
     still stamps `_last_activity`, and `_unload_now` (which would clear it)
     returns early because nothing is loaded.
  2. More than `idle_unload_minutes` later, load-on-arm succeeds.
  3. `_background_load` only sets `_last_activity` when it is `None`, so the
     stale time survives, and the next 5 s silence tick unloads the model
     **while the user is talking**.
  4. The transcription pays the cold load again.
- **Confidence:** Confirmed by test
  (`test_preload_after_failed_load_is_not_immediately_idle_unloaded`).
- **Fix:** always stamp `_last_activity = clock()` (under `_state_lock`) after
  a successful load. Don't stamp it in `_finish_transcription` when the
  backend isn't loaded.

### L-6: A CPU-fallback load that fails mid-transcribe shows a generic error, not the actionable one

- **Where:** `src/dictatem/transcribe/fallback.py:90` and `:102`.
- **Scenario:**
  - MLX fails mid-transcribe, and the composite loads the CPU fallback inline.
    That load is outside the lifecycle's `ModelLoadError` wrapping.
  - Offline, the fallback weights aren't cached (ADR-0013), so the raw error
    surfaces as `unexpected_error`. The user sees "Transcription Error"
    instead of the classified "Model Download Failed — connect once…".
  - In the confirm pass the same failure becomes `confirm_failed`, which
    shows as a silent say-again.
  - Separately, after a fallback, `TranscribeLifecycle` still carries the MLX
    `model_name`/`device` (`daemon.py:2481-2487`), so any diagnosis names the
    wrong model.
- **Confidence:** Confirmed by test
  (`test_fallback_load_failure_mid_transcribe_is_a_classified_model_error`).
- **Fix:** raise a marker that the lifecycle classifies as `ModelLoadError`,
  or have the lifecycle re-run `_ensure_loaded` after the latch. Report the
  fallback's model in the diagnosis.

### L-7: `yue` on a non-large-v3 Apple-GPU model trips the MLX fallback

- **Where:**
  - `src/dictatem/transcribe/language.py:48`
  - `config.py:573`
  - README line 330 lists `yue` as an ordinary code
- **Scenario:** mlx-whisper's tokenizer only knows `yue` on 100-language
  (large-v3) models. On the Apple-GPU-low tier (`small`) it raises
  `ValueError`, which the composite treats as an engine failure. The session
  latches to CPU with "MLX failed while transcribing". This happens with
  `language = "yue"`, or with `"auto"` on a `yue-Hant` macOS display language
  (via the OS-language fallback). faster-whisper doesn't crash on it; it just
  drops the token.
- **Confidence:** Plausible; not run on a Mac.
- **Fix:** map `yue` to `zh` for models without the 100th language token, and
  don't use `yue` as the OS fallback for those models.

### L-8: `large-v2` and `turbo` model names aren't mapped for MLX

- **Where:** `src/dictatem/transcribe/mlx_models.py:45-56`.
- **Scenario:** faster-whisper accepts both names, but `_MLX_REPOS` has
  neither. An Apple-Silicon user with one of them who switches to
  `device = "mlx"` gets `UnknownMlxModelError` and ends up on the CPU row
  instead of the GPU.
- **Confidence:** Confirmed by reading the code.
- **Fix:** add the aliases (`mlx-community/whisper-large-v2-mlx`;
  `turbo` → large-v3-turbo).

## Checked and found sound

- **Stale results after Esc:** the epoch tagging (`session.py`, both queues),
  including the confirm pass's second worker and a cancel mid-Transform.
- **Errors leaving the daemon stuck:** every worker exception kind maps to a
  recover-to-idle, so the state machine can't be stranded in `TRANSCRIBING`.
- **Hook callbacks:** they catch everything and always call `CallNextHookEx`.
  A failed masked replay passes the original key-up through, so no key is
  left stuck.
- **Tagged injections:** Dictatem's own `dwExtraInfo`-tagged events never
  reach the classifier.
- **Modifier wait and input settle:** both are bounded. A `ModifiersHeldError`
  holds a regular dictation, and discards a Trigger Fire while keeping Last
  Paste armed.
- **Most-recent dictation buffer:** written *before* `paste()`, so a failed
  paste never loses the dictation (ADR-0023).
- **Win32 clipboard handles:** `GlobalAlloc`/`GlobalLock` ownership and
  freeing, and `save`/`restore`/`copy` always closing the clipboard.
- **Paced typing:** never splits a surrogate pair or grapheme. The
  Backspace-unit splitter handles ZWJ, flags, keycaps and CRLF.
- **Single-instance lock:** Qt 6 `QLockFile` doesn't steal a *live* owner's
  lock even when the file is older than `staleLockTime`; probed by hand with
  two processes. The tray-Restart wait path is also sound.
- **Config validation:** wrong types, `bool` given for an `int`, an invalid
  language code, a sample rate other than 16 kHz, and a whole number for a
  decimal setting are each reported once and replaced by the default. A
  config with any problem stays read-only for the session.
- **Language selection:** the sure-or-fall-back rule, OS locale mapping
  (`zh-Hant`, `pt-BR`, `pt_BR.UTF-8`, unknown → `None`), and English-only
  `.en` models given another language.
- **MLX fallback and platform reconcile:** the fallback latch fires once, and
  an `mlx` pin on Windows, an Intel Mac, Rosetta or macOS below 14 reconciles
  to the right CPU row.
- **Fuzzy Trigger Words:** "Past."/"Waste."/"Taste." firing `paste`, and
  "Clean up." firing `polish` when armed, are accepted consequences in
  ADR-0028 and pinned by the golden table. Not reported as bugs.
